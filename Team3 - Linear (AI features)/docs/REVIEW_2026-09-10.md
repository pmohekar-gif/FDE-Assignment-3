## 1. Governance → agent failure

### Root causes (four defects, all reproduced before fixing)

**RC-1 — the protected-surface scope match had its arguments reversed.**
`CodingSessionService._restricted_paths` tested `fnmatch(surface_glob, scope_pattern)`.
Both directions were wrong:

- An approval narrowed to a concrete file (`services/billing/retry.py`) never matched the
  surface glob it lives under, so `services/billing/**` stayed on the restricted list and
  the session failed with `agent changed restricted files: services/billing/retry.py` —
  the very file the named owner had just approved. **Every** protected-surface delegation
  failed after approval. Reproduced on `PAY-4471`.
- A broad grant (`services/**`) matched every nested glob, silently unlocking the
  separately owned, irreversible `services/billing/ledger/**` surface.

**RC-2 — no scope-existence check, so a doomed session ran to a useless failure.**
The warrant's scope comes from the issue's declared `path_hints`. 21 of the 31 seeded
issues declare paths inside the control plane's own tree (`src/warrant/**`, `tests/**`,
`docs/features/**`), which the coding-session target checkout does not contain. A real
`codex` run there has nothing to edit, exits 0, and the session dies with
`agent_failed: agent completed without producing a reviewable diff` — naming neither the
scope nor the repository. **This is the exact message reported for `CHIR-1103` and
`GAU-3103`.** Physical evidence: the four abandoned worktrees under
`.runtime/coding-sessions/` are branched `agent/pay-4471-…`, `agent/gau-3103-…`,
`agent/chir-1103-…` and contain **no agent-written file at all** and no `src/` directory.

**RC-3 — the secret scanner redacted Git's own metadata and failed the session.**
`_create_diff` ran `SECRET_PATTERNS` over the whole patch text, including
`index <old-blob>..<new-blob> <mode>`. The `card_pan` pattern (13–19 digits with optional
separators) matches an abbreviated blob pair that happens to be digits and dashes, so an
ordinary diff was rejected as `diff contains secret-like material and was redacted` —
non-deterministically, depending on the hashes Git computed. It also destroyed the
recorded artifact, which then no longer named the revisions needed to reproduce the diff.
Reproduced on `GAU-3103`.

**RC-4 — an ambient agent-CLI hook denied the prompt, and the product took the blame.**
Found on a real `codex` run of `CHIR-1104` *after* the fixes above. The transcript:

```
hook: SessionStart
hook: SessionStart Completed
hook: UserPromptSubmit
hook: UserPromptSubmit Blocked
```

A `UserPromptSubmit` hook rejected the prompt, so the model never received the task and
the CLI exited 0 having done nothing. This project registers only `PostToolUse` and
`Stop` in `.codex/hooks.json` — the blocking hook is in the operator's own Codex
configuration, which a session inherits because `HOME` and `CODEX_HOME` must reach the
subprocess for it to authenticate. On the evidence a session can see, this is
indistinguishable from "the agent read the code and decided no change was needed": exit 0,
empty diff, approved paths present. One transcript line separates them, and they have
opposite remedies.

Now: `blocked_hooks()` reads the CLI's hook lines; a denial always records an
`agent_hook_blocked` event (even when the run produced a diff, since a worked-around
`PreToolUse` is not a failure but is something a reviewer must see); and when the diff is
empty *and* a turn-gating hook was blocked, that is reported as the cause ahead of every
other explanation, naming the agent-config files that exist on the machine. The session
timeline now renders `agent_hook_blocked`, `empty_diff_diagnosed` and `scope_preflight` in
plain language, with an amber pip rather than a neutral one. Recorded as `D-ENG-024`; the
underlying isolation gap was `IC-008` (renumbered from a duplicate `IC-004`), closed by
`CODING_AGENT_ISOLATED_HOME` (`D-ENG-025`) once the diagnostic identified the denying
hook as belonging to an unrelated project rather than to this one.

## 2. The four delegation actions

### What they are supposed to do, and what they did

| Action | Intended meaning | Delivered behaviour | Now |
| --- | --- | --- | --- |
| **Approve as named authority** | Issue a warrant for the whole proposed scope | Correct, **but** unticking surfaces and pressing it discarded the selection and granted the full scope anyway | Server refuses a selection that differs from the proposal and names the `narrow` action; the client blocks it first |
| **Issue only the selected scope** (`narrow`) | Issue a warrant limited to the ticked surfaces; the agent's write set and restricted-path list derive from that narrower scope | Scope narrowing itself was correct and validated. **But** it skipped the concurrent-warrant supersede path, so narrowing onto a surface an active warrant already held issued a *second* live warrant over the same surface with no revocation | The supersede path now runs for both authorising actions |
| **Hold (defer)** | Postpone without denying: no warrant, delegation leaves the approval queue, an approver can lift the hold later | A silent dead end. Two locks made it permanent — `decide()` refuses any status but `awaiting_approval`, and `approvals` is `UNIQUE(delegation_id)` — so it was Deny under a gentler label. Nothing in the product read `status='deferred'` | `POST /v1/delegations/{id}/resume` lifts the hold back to `awaiting_approval`, gated on the same approver set; both steps stay in the audit ledger |
| **Deny** | Final; a new delegation must be submitted | Correct, but invisible | Correct, and now visible |

### Additional fixes

- **The authorising decisions were not audited.** `approve` and `narrow` emitted only
  `warrant_issued`; the named approver's rationale never entered the hash-chained ledger
  for exactly the two actions that grant authority. `approval_approve` and
  `approval_narrow` events are now appended, carrying the rationale, the issued scope, the
  proposed scope and whether it was narrowed. Chain verification still passes.
- **The recorded decision was write-only.** `get_delegation` never read the `approvals`
  table, so a held or denied delegation showed no approver, action or rationale anywhere —
  it simply lost its buttons and looked undecided. It now returns an `approval` block plus
  a `resumable` flag, rendered as a "Recorded human decision" panel, and held/denied rows
  carry an `ON HOLD` / `DENIED` chip in the triage queue.
- **The audit timeline mis-coloured a hold.** `'den' in event_type` coloured
  `approval_defer` by accident; matching is now on whole event names, with a distinct
  amber pip for a hold.
- The Human-gate rail now states, in one line each, what all four actions do.

## 3. Code Intelligence

### Is it real?

**Yes, the retrieval half is genuinely real.** It reads files from `REPOSITORY_ROOT` on
disk, enumerates them via `git ls-files` (or `os.walk` plus a hand-written `.gitignore`
matcher), extracts symbols and imports, persists a revision-keyed metadata index in
`repository_indexes`, and ranks evidence with a symbol/dependency graph (definition 100 /
call site 80 / import 70) over a grep pass with additive path, symbol and language
heuristics. Citations are real `path:start-end` line numbers, secret-redacted and capped
at 12 snippets / 12,000 characters. Nothing in that path is fixture-backed.

### What was not real

`CODE_INTELLIGENCE_REFINEMENT_EXECUTION.md` promised the provider "receives only the
final redacted, bounded evidence set". It received **one composed sentence** of module
names and line labels — not a single line of code — so the model could only re-word a
template while the UI labelled the output "AI synthesis". Fixed:
`_provider_facts()` now passes the composed summary plus exactly the budgeted,
already-redacted snippets the operator sees, each labelled with its citation; the
contextual Agent likewise passes its deterministic facts.
`tests/unit/test_code_synthesis_grounding.py` pins the contract in both directions.

Also corrected:

- Two shipped example queries — "Who wrote the payment processing logic?" and "When was
  the search feature added?" — cannot be answered by this index at all (no authorship, no
  history; `_git` is restricted to `rev-parse`/`ls-files`/`diff`). They returned
  confident-shaped keyword matches. Replaced with answerable examples.
- The fixture provider was badged "AI synthesis · fixture" while the answer body began
  `SIMULATED fixture answer to …`. It is now badged "SIMULATED synthesis · deterministic
  fixture, no model called".
- Dead client JS disabled two element ids (`file-filter`, `symbol-filter`) that no element
  carries. `/v1/code/files` and `/v1/code/symbols` remain deliberately API-only.

### Git repository URL → index → ask → link to ticket: **out of scope** (D-ENG-022)

- `assignment3.md` asks for an issue workflow with AI triage, duplicate detection,
  semantic search, or safe agent delegation. Remote code search is none of those; the
  graded core is the delegation path.
- Accepting a user-supplied URL adds a server-side request surface, unbounded disk growth,
  third-party credential handling and a supply-chain path into the same process that runs
  coding-session worktrees — in a product whose entire claim is bounded authority. That is
  a threat-modelling task, not a feature increment.
- The existing boundary is already disclosed (`PB-002`, `IC-002`), and the practical need
  is met in one command: clone locally and point `REPOSITORY_ROOT` at it, which is exactly
  what `make demo-repo` does.
- Finding → ticket linking already exists as a handoff: impact preflight builds a
  citation-backed text block that lands in the issue's comment box, and posting it
  persists it on the issue with the citations intact. A dedicated `finding → issue` table
  is not needed for the assignment.

6. **Draft-PR publication is unexercised.** `PR_PUBLISHING_ENABLED=true` but it needs `gh`
   authenticated and a GitHub `origin` on `REPOSITORY_ROOT`; the demo checkout has no
